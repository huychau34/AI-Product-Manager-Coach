LLMs, tokens & hallucinations for product managers

You'll talk to engineers about model limits daily. An LLM predicts the next token from context. It has a limited context window and can produce confident but wrong text (hallucination). Product implication: design for verification, not blind trust.

An LLM (large language model) is trained on huge amounts of text to do one thing: predict the next token. A token is a word or a piece of a word, and everything about an LLM - how much it can read, how much it writes, what it costs and how fast it is - is measured in tokens. It has no database of facts; it generates plausible text from patterns it learned.

That design creates limits you must plan around. The context window is the model's working memory for one request; beyond it, earlier content is dropped or must be summarised. It has a knowledge cutoff, so it doesn't know recent events unless you give them to it. It is non-deterministic: the same input can produce different outputs. And it can hallucinate - write fluent, confident text that is wrong - because it optimises for plausible, not true.

The product implication: design for verification, not blind trust. Ground answers in your own data, show sources, let users edit and undo, allow the model to say "I don't know", and keep humans on high-stakes decisions. Remember that cost and latency grow with tokens, so long prompts and long chats cost more. Good questions for your engineers: which context window do we use, what happens when we exceed it, and how do we measure the hallucination rate?
